## 设计与实证（证据=gradle 缓存 neoform 反编译源码 + javap）

- **单一 CRAFTING 类型**：ShapedRecipe/ShapelessRecipe 均不覆盖 getType()，一个任务类吃两类（本体 0.2.9 与 libs 内生态 jar 零 CRAFTING 注册，无同键覆盖；maidtavern/fox_trot_brew 不在本机 libs，残余风险由真机菜单验证兜底）。
- **CraftingInput.of(w,h,layout) 内部恒做最小包围盒裁剪**（ofPositioned）：shaped 按配方（JSON 已 shrink 的 w×h，空白=Ingredient.EMPTY）原位摆放，与 ShapedRecipePattern.matches 的「裁剪后尺寸严格相等」要求天然一致；shapeless 紧凑散放（matches 走 stackedContents.canCraft，与位置无关）。
- **getRemainingItems(input) 无 Level 参数**（1.21.1，与 1.20 Forge 形态不同）——牛奶桶→空桶返还走此项，非空项交还女仆。
- **hurtAndBreak(int, ServerLevel, @Nullable ServerPlayer, Consumer)** 原版显式判空（本里程碑未用，M9 砧板依赖此结论）。
- **CraftingTableBlock 无 BlockEntity**：`getBlock() instanceof CraftingTableBlock` 判定（茶壶补放位纯状态判定先例）。
- 失败路径：中途缺料=已抽回包+WARN（30s 窗）；任一配料缺失=静默等待（F-190 逐份齐备预检）；matches 不符=回包+WARN（不静默装正常）。

## v0.2.2 自锚点设计变更（2026-10-20，as-built——轮次明细与收口状态以审查台账为准）

- **背景**：0.2.0 `instanceof CraftingTableBlock` 判据被 VisualWorkbench「原键换实例」躲过（Puzzles Lib `RegistryEntryAddedCallback(Registries.BLOCK)` 把 `minecraft:crafting_table` 键下的 Block 实例换成自家 BaseEntityBlock 子类）；0.2.1 注册表键判据（`BuiltInRegistries.BLOCK.getKey==minecraft:crafting_table`）测试服仍卡死（原因无法从本机证实）——环境方差不可控，设计定调**去外界工作方块依赖：女仆空手自合成**（`cookTick`/菜单口径/FOOD 过滤/`craftingTable.enabled` 开关全部不动，0.2.1 已过三轮审查；0.2.1 锚点判据 `isCraftingAnchor` 与 anchor-absent/all-busy WARN 分支删除）。
- **三段式 searchWorkBlock（as-built）**：
  - ① 骑坐返回 `maid.blockPosition()` 原地合成（就坐路径距离门 distSqr=0 天然通过，本体自带「自身坐标当椅子」先例，`CHAIR_POS=maid.blockPosition()`）；
  - ② 站立：`getBrainSearchPos()` 为中心 **tag 级初扫**（凳邻位 + `BlockUsageManager.getUserCount<=0`）→ **凳位级空闲过滤**——对每个 marker 取其 below() 四邻中 `TagBlock.SIT_BLOCK` 命中的凳位，要求 `isSeatFree`（**精确复刻本体 isChairAvailable**：`new AABB(seat)` 内 EntityMaid 为空或仅自身，all.java:5744-5747），同凳多 marker 只保留距女仆最近者（HashMap 显式距离比较，不依赖 SearchUtils 返回顺序），最终取最近 marker；
  - ③ 无可用凳位（初扫空 / 凳位全被占）**返回 null** + WARN（键=`消息码:女仆UUID`，per-maid 防跨女仆压制，30s 窗 LOG_WINDOW_MAX=64 有界）：`no-seat-neighbor` / `seat-all-busy`，消息体含订单号、女仆名、坐标。**null 语义（F-191）**：本体两消费端均优雅处理 null——站立路径 `MaidApproachCookBlockTask.search` 以 `pos != null` 守卫+isWithinRestriction+逐凳 isChairAvailable（all.java:5715-5729），就坐路径 `MaidSearchCookBlockTask` 以 `pos != null && distSqr<=4.0` 守卫（all.java:6124-6146）；`CheckRateManager` 节流在 searchWorkBlock 调用**之前**（all.java:5564-5575，放行时置 60+rand(60) tick≈3–6s，all.java:8080-8092）——null 后重试节奏恒为 3–6s+请求留队，是本体的「等待」词汇，**「每 tick 重扫」经实证不存在**。
- **isValidWorkBlock 非恒真（fork 实证驱动；0.2.3 F-197 收窄）**：`maid.blockPosition().equals(pos)` → true（就坐路径 pos=搜索时的 maid.blockPosition()、站立到达后 blockPosition==marker，两路径天然覆盖；0.2.2 的 `isPassenger() ||` 恒过分支已删——骑坐中校验外部 marker 不再恒过，车辆移位即失效重搜）；否则 `hasSeatNeighbor(level, pos)`（复刻本体站立路径接受判据 all.java:5719，凳被拆→false）。两面依据：本体 MaidCookingTask 运行中复验 false→stop 重搜（唯一调用点 all.java:5874）；营业 fork `CookingTargetRedirector.resolveAssignedTarget`（fork 源 31-56 行）以本方法作分配工位**活性校验**（fork `CookingBridge.selectWorkPosForMaid` 选位首步调本类 searchWorkBlock，CRAFTING 营业单 targets[0]=凳邻位 marker）——恒真会让「凳在发布后被拆」的失效工位永远过检，mixin 不回退→营业单挂 ASSIGNED 硬超时。
- **残余竞态（如实声明）**：两女仆同 tick 选中同凳（isSeatFree 快照间竞态）由本体走位阶段 `isChairAvailable` 仲裁，败者 3–6s 后重扫；任务侧无 mixin，**无法观测本体走位阶段的拒绝**，不做超控。
- **已知约束**：站立合成要求搜索半径内有 cook_stool/chair tag 凳位——**主模硬约束**（addon 无法绕过；原版楼梯/半砖不在 tag，厨房本就摆凳实际影响≈无）；站立路径 body 阶段拒绝不可观测（同上）；骑坐合成零依赖但依赖 SIT_WHILE_COOKING 体系把女仆先送上凳（两路径互为补充）；0.2.1 键判据未命中根因不再重要（自锚点已无方块依赖），若日后要查需服务端 debug 日志。
